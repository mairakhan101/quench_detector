## 2026-08-25 (3)
- **What:** Added `hts_tape_env/physics_bi2223.py` — a second, separate conductor physics module (not a mode flag on `physics.py`) for Bi-2223 tape, plus `scripts/compare_rebco_bi2223.py` comparing its runaway boundary I*(T0) against REBCO's.
- **Why:** User wants REBCO and Bi-2223 kept as genuinely separate models, per this project's own reference paper (Marchevsky & Prestemon 2024, `10.1088/1361-6668/ad20fe` — confirmed this is the *same* paper `physics.py` is already based on, and the user's "BI22e" was Bi-2223, not Bi-2212). The paper's own Discussion says ReBCO is "far more spatially inhomogeneous than the Bi-2223 conductor" — its Sec. 2 REBCO model (physics.py) assumes electrical uniformity + a Cu/SS current-redistribution model (eq. 7-8); its Sec. 3 Bi-2223 model uses *measured* I_c(T)/n(T)/η plugged into the no-stabilizer heat balance (eq. 2-4) instead, with no redistribution model. That's a real, paper-stated difference in assumptions, not just different constants — hence a separate module.
- **Result/metric:** Cross-checked against the paper's own validation number: at T0=77.16 K (their LN2 test point) the reconstruction gives I*=275.8 A vs the paper's reported ~260 A (+6.1%), reasonable given the caveat below. **Important caveat:** the paper does not publish a digitized I_c(T)/n(T) table for Bi-2223 (Fig 6(e) is a scatter plot with only two numbers given in text: T_x=91.35 K where I_c→0, n=1 there) — `IC_ANCHOR_A` and the `n_value()` anchor table in `physics_bi2223.py` are read off that figure by eye and flagged loudly in the module docstring; re-digitize the figure if this needs to be trustworthy past ~10-20%. Also found and guarded a real failure mode: above T0≈81 K the crude piecewise n(T) degenerates as n→1 near T_x and `solve_runaway` was returning a nonphysical current spike (3000+ A) instead of a real interior maximum — now detected (`sanity_cap_factor`) and returned as NaN rather than silently reported; comparison script restricted to the validated ~77-80.5 K range accordingly. `models/rebco_vs_bi2223_runaway.png` shows both I*(T0) curves side by side (different, non-overlapping T0 ranges — each conductor swept only where its model is actually characterized).
- **Next:** (1) Someone should re-digitize Fig 6(e) properly (e.g. WebPlotDigitizer against the source PDF) to replace the eyeballed `IC_ANCHOR_A`/`n_value` anchors with real numbers, which should also fix the >81 K breakdown. (2) The REBCO spatial-inhomogeneity side of this (which the paper flags as unaddressed) is really `fem_env.py`'s job, not a new invented Ic(x) formula — connect the two rather than build fabricated spatial physics. (3) No Bi-2223 heat-capacity/time-margin model yet (thermal.py's C_per_m is Cu/SS-specific); add one if the adiabatic time-margin comparison is wanted for Bi-2223 too.

- **Why:** The concrete ask was "inference on FEM files from the sim-trained model" — this is the sim-to-FEM generalization check: does a surrogate that has only ever seen the lumped analytic solver's trajectories correctly flag risk on genuinely different (real, spatially-resolved) physics.
- **Result/metric:** Result is a real generalization gap, not a clean pass: the surrogate's `breach_prob_pred` **never crosses 0.5 on either FEM runaway run** (r0p95 quenches at FEM step 48, r0p99 at step 45) — both are misses by this model/threshold. On the 4 stable FEM runs it correctly stays quiet (no false alarms). Plot saved to `models/fem_surrogate_inference.png` (margin_pred/breach_prob_pred vs t, FEM quench point marked). Plausible cause: the analytic env's margin/breach labels are scaled to `physics.py`'s (I,I*) dynamics, which move on a different timescale/shape than this FEM sweep's ratio-driven runaway — consistent with the dump_threshold-granularity caveat already logged above.
- **Next:** (1) Don't retrain on FEM data yet (still only 6 trajectories — too few); instead check whether a *rescaled* threshold on `margin_pred`/`breach_prob_pred` (not 0.5) would catch these two FEM runaways, as a cheaper first fix than retraining. (2) Once more FEM sweep points exist, consider fine-tuning or a small joint sim+FEM training set. (3) Revisit alongside the dump_threshold retuning already queued above — likely the same root cause.

## 2026-08-25
- **What:** Added `hts_tape_env/fem_data.py` (loader) and `hts_tape_env/fem_env.py` (`FemReplayQuenchEnv`) to bring in the FEM ground truth at `//eagle/fanc_ldrd/magnets_fem/sweep.h5` — a 3D electrothermal transient solve with a real sensor layout (16 RTDs, 20 voltage taps, 2 current-lead voltages, 2 unwired Hall-probe placeholders) at 6 current-sharing-ratio operating points (r0p5..r0p99; r0p95/r0p99 thermally run away, the rest settle).
- **Why:** Move past the lumped single-conductor analytic model (physics.py) toward real spatially-resolved telemetry, matching the actual sensor geometry a deployed detector would have. `fem_data.py` reshapes the sweep into a rollout.py-style long table (same column names where a physical analog exists — T0_K/I_A/voltage_V/T_surface_K — NaN for columns with no FEM analog, e.g. Istar_A/lam, documented in the module docstring so nothing gets silently mislabeled). `fem_env.py` goes further: a Gym env whose *observation* is the full spatial grid (I0 + all 16 RTDs + all 20 V-taps, ordered by x-position) rather than one lumped point, replaying the FEM trajectory directly step-by-step so no PDE/boundary-condition solve is needed at run time. Same Discrete(2)/info["margin"]/info["runaway"]/dump_threshold contract as QuenchDetectorEnv, so `controllers.py`'s oracle_controller/evaluate() work against it unmodified.
- **Result/metric:** Loader smoke-tested: 573 rows over 6 episodes (80-101 steps each), quench_step correctly lands at step 45/48 for r0p99/r0p95 (Tmax crosses 300 K), NaN elsewhere as expected. Env smoke-tested with `oracle_controller`/`evaluate()` over 50 resets — runs cleanly, margins/rewards physically sensible (runaway episode terminates at margin≈0 with reward_missed when never dumped; safe episode truncates at t=2 s with reward_step). **Caveat surfaced:** the FEM output timestep is adaptive (0.05 s early, refining to 0.002 s then settling at 0.01-0.02 s near the ramp/runaway region -- not fixed, use each row's `t_s`), and even so Tmax rises fast enough near runaway that margin can skip clean over the (0, dump_threshold) "timely dump" band between two adjacent steps — the oracle controller's hit_rate was 0/50 in the smoke test for that reason, not a bug; dump_threshold or the margin definition will need retuning for this env's timestep granularity before it's used for real controller evaluation. Also note: only 6 fixed trajectories exist (+ optional sensor noise), so this is a validation/spatial-prototyping env for now, not a large-scale RL training env.
- **Next:** (1) Retune dump_threshold (or redefine margin, e.g. against dT/dt instead of absolute Tmax) so timely dumps are reachable at this env's step resolution. (2) Validate the analytic model's I*/T* against the FEM runaway points (r0p95/r0p99) as a physics cross-check. (3) If more FEM sweep points become available, extend fem_env.py's episode sampling beyond the current 6 fixed runs.
